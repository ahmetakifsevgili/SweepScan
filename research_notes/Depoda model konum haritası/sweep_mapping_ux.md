# Sweep-to-Location Mapping, Map Freshness, and Lookup UX (single small shoe stock room, 2026)

Scope: a phone app sweeps one column of stacked shoe boxes, reads a QR location label (e.g. "S2-07" = row 2, column 7) at the start, records the box barcodes in that column, and later answers "where is model 0159 2000?". Research was web-based. Most WMS sources are vendor docs written for large warehouses. Academic numbers come from multi-store retailers, not single shops.

## 1. "Scan location, then scan items" workflows: how WMS products prevent location errors

### Takeaway
Mainstream WMS products all use a "location first, then contents" pattern. Their main defense against a wrong location is *positive verification*: the operator must scan the location barcode, or enter a short random check digit printed on the label, before the system accepts anything. I found no vendor docs on two labels in view or a sweep that runs into the next column, because handheld scanners read one code per trigger pull. Those cases are specific to a camera sweep and need their own design.

### Cited Findings
- Odoo Barcode (Enterprise) supports a location-first count. The user scans a location barcode, picks "Count Entire Locations", and the app lists the products assigned to that location. Each product is then scanned to increase its count. A setting can hide the expected quantity so counters don't see the system number. This needs Storage Locations enabled, and Barcode is Enterprise-only. — [Odoo 18 docs: Adjust inventory with barcodes](https://www.odoo.com/documentation/18.0/applications/inventory_and_mrp/barcode/operations/adjustments.html)
- Microsoft Dynamics 365 SCM "spot cycle counting" lets a worker count a location at any time without open count work. The worker starts by entering or scanning the location ID. Counts create cycle-count work that must be *accepted* before it posts to inventory, so there is a review step between the count and the update. — [Microsoft Learn: Cycle counting](https://learn.microsoft.com/en-us/dynamics365/supply-chain/warehousing/cycle-counting)
- Infor WMS lists three RF verification modes: *Location Verification* (scan or enter the location number), *Check Digit Verification* (enter a single-character check digit printed on the location label, which replaces the location prompt), and *No positive verification*. For putaway the location is always a required confirmation. — [Infor WMS: RF-directed putaway verification methods](https://docs.infor.com/wms/2022.x/en-us/useradminlib/sceputug/pwi1612894067799.html)
- Check digits are usually short random codes, often 2–3 characters, not derived from the location number. Because they are random, operators can't type the location from memory without being there. In Dynamics AX, when check digits are enabled each one must be unique within the warehouse. A location without a check digit must be scanned instead. — [Stoneridge Software: Check digits in Dynamics AX WMS](https://stoneridgesoftware.com/check-digits-dynamics-ax-advanced-warehouse-management/); [Iptor: Location check digit validation](https://ip1help.iptor.com/ibs-bookmaster-7-9/ip1-product-documentation/user-guides/warehouse-rf-menu/location-check-digit-validation/) (summarized via search snippets)
- Known weakness: a patent notes that check-digit duplicates at adjacent or related locations can cause errors. — [Patent US8868519B2 (via search snippet)](https://eureka.patsnap.com/patent-US8868519B2)
- Some vendors offer camera or sensor put-away verification with no check digit, using cameras on forklifts. This is evidence that camera-based location confirmation is an accepted pattern. — [Vimaan: Put-away verification](https://vimaan.ai/put-away-verification)

### Inferences
- **Forgotten location scan.** WMS apps prevent this with a modal flow: the item-scan screen can't open until a location is set. For SweepScan this means a sweep that has not decoded an "S#-##" QR should not commit box records to any location. Hold them as "unassigned" and ask for a location at the end, rather than inheriting the previous column's label.
- **Wrong location scanned.** The WMS answer is to make the location label unambiguous and machine-read. Never accept a typed location in the sweep flow. Show the decoded location in large text and speak or beep it at sweep start (e.g. a distinct tone plus "Row 2, Column 7"), so a mismatch with where the user is standing is caught immediately. This is the camera equivalent of a check-digit prompt.
- **Two location labels in view.** Handheld WMS has no direct precedent. A reasonable rule: accept a location only when exactly one location QR is decoded and it is reasonably centered or large. If two different location QRs are seen in the first frames, pause and ask the user to center one.
- **Sweep crossing into the next column.** Also no direct precedent. Options, all inferences: (a) if a different location QR appears mid-sweep, end the current column and start a new one, as if the user had scanned a new location; (b) put an *end-of-column* label at the bottom of each column, or the same QR at top and bottom, as a bracket; (c) flag boxes seen after a large lateral motion for review.
- **Confirmation before commit.** Dynamics' "count must be accepted before posting" step suggests a short review screen per column ("S2-07: 9 boxes, 4 models. Save?"). It should be one tap or auto-accept after a timeout. It should not overwrite the column silently.

### Gaps
- I found no published error rates for wrong-location scans with check digits versus plain location scans.
- I found no vendor documentation on camera sweeps where several location labels may be in frame. This is SweepScan-specific and should be tested in the field.
- I did not find specific sources on beep and haptic conventions (good-read and bad-read tones) in WMS apps. This is common industry practice, but uncited here.

## 2. Positions within a column (top-to-bottom order): worth storing?

### Takeaway
I found no source that measures the value of storing a box's slot height inside a stack versus only its column. The record-accuracy research below shows that even *location-level* records degrade fast. A slot index is even more volatile, because any pick from the middle of a stack reshuffles everything above it. Store it as a cheap hint, not as primary data.

### Cited Findings
- Record accuracy is poor even at the SKU-quantity level: 65% of ~370,000 records were inaccurate across 37 stores of one retailer. — [DeHoratius & Raman 2008, Management Science 54(4):627–641](https://pubsonline.informs.org/doi/10.1287/mnsc.1070.0789)
- At "Beta", 16% of items that shoppers asked associates for help with could not be found even though they were in stock. They were in the wrong storage area, aisle or location. — [Chicago Booth Review: First Measure, Then Manage](https://www.chicagobooth.edu/review/first-measure-then-manage)
- Dynamics 365 has a "location license plate positioning" feature for ordered positions within a location. This shows enterprise WMS does model sub-location order in some cases, though the docs were not read in detail. — [Microsoft Learn: Location license plate positioning](https://learn.microsoft.com/en-us/dynamics365/supply-chain/warehousing/location-license-plate-positioning)

### Inferences
- Storing the order of boxes within a sweep costs almost nothing, because the sweep already sees them top to bottom. The UI can use it as "roughly upper or lower half" ("S2-07, near the top"), labeled approximate and dated with the sweep time.
- Don't build features that rely on exact slot indexes, such as "3rd box from the top", unless field tests show stacks stay stable between sweeps.

### Gaps
- I found no empirical data on how often individual stacks are reshuffled in shoe stock rooms. Consider logging it from repeated sweeps (compare the slot order of the same column across sweeps).

## 3. Keeping the map fresh: staleness, accuracy numbers, re-count cadence, multi-location items, sales

### Takeaway
Retail inventory records are wrong most of the time without regular audits: 51–65% of SKU records are inaccurate in published studies. The errors grow steadily from unrecorded events. Counting more often measurably reduces them. Industry practice is ABC-weighted cycle counting. Recent research models record quality as *decaying over time*, which supports showing a "last seen" timestamp and a confidence that falls with age.

### Cited Findings
- **65% inaccurate:** DeHoratius & Raman found 65% of ~370,000 inventory records inaccurate across 37 stores of one retailer. They found auditing practices reduce inaccuracy, while store complexity and distribution structure increase it. About 26.4% of IRI variance lies between product categories and only 2.7% between stores. — [DeHoratius & Raman 2008 (INFORMS)](https://pubsonline.informs.org/doi/10.1287/mnsc.1070.0789); [EconPapers listing](https://econpapers.repec.org/RePEc:inm:ormnsc:v:54:y:2008:i:4:p:627-641)
- **51% accurate:** Kang & Gershwin report that inventory accuracy at "Company A" stores averaged only 51% (about half of SKUs had exactly correct records). They show that small, unrecorded stock loss accumulates over time into large record errors and severe stockouts. — [Kang & Gershwin, "Information Inaccuracy in Inventory Systems: Stock Loss and Stockout" (MIT)](https://dspace.mit.edu/bitstream/handle/1721.1/74618/2-854-fall-2004/contents/lecture-notes/kang_gershwin_04.pdf)
- **Audit frequency matters:** Gamma stores audited twice a year had substantially fewer errors than stores audited once a year. Execution problems cut Gamma's profits by more than 10%. At Beta, misplaced items cut profits by more than 25%, and awareness campaigns plus store training reduced misplaced items by 22%. — [Chicago Booth Review](https://www.chicagobooth.edu/review/first-measure-then-manage); [Raman, DeHoratius & Ton 2001, California Management Review](https://cmr.berkeley.edu/2001/05/43-3-execution-the-missing-link-in-retail-operations/)
- **Misplacement versus record errors:** In a specialty-retailer audit, 60% of stockouts were products that were in the store but where shoppers couldn't find them, and 24% were due to inaccurate records. At Borders, about 18% of customers who asked for help hit a "phantom stockout". The search summary also notes that backrooms are where misplaced or forgotten products pile up. — [DeHoratius & Ton, Springer chapter (summarized via search; the full text was behind a login)](https://econpapers.repec.org/RePEc:spr:isochp:978-1-4899-7562-1_4); [MDPI review](https://mdpi.com/2071-1050/13/17/9490)
- **Information decay model:** Chuang, Oliva & Kumar (2022, *J. Operations Management* 68(2):130–152) model *group-level information decay* in continuous time. They estimate the unseen hazard rate of record degradation from correction records and derive an inspection policy that beat both the retailer's routine and an industry benchmark. — [EconBiz record](https://www.econbiz.de/Record/group-level-information-decay-and-inventory-inspection-an-empirical-analytical-approach-chuang-howard-hao-chun/10014086559) (abstract only)
- **Audits pay off:** In grocery data (~24,000 SKUs, 11 stores), an inventory audit produced an "11% store-wide sales lift". All of it came from items whose system inventory exceeded actual inventory. IRI was higher with more inventory and more frequent restocking. — [Rekik, Oliva, Glock & Syntetos, arXiv 2506.05357 (2025)](https://arxiv.org/abs/2506.05357)
- **Cycle-count cadence (practitioner guidance, not standards):** common ABC schedules are A monthly, B quarterly, C yearly. More aggressive versions are A weekly, B monthly, C quarterly. Accuracy targets are often A 99%+, B 97%+, C 95%+. Guidance also suggests recounting after any variance on an A item. These come from vendor blogs, so treat them as common practice. — [Cleverence: Cycle Count Guide](https://www.cleverence.com/articles/business-blogs/guide-cycle-count-4729/); [Fishbowl: Cycle counting](https://www.fishbowlinventory.com/blog/inventory-cycle-count-key-steps-and-best-practices); [TechTarget](https://www.techtarget.com/enterprise-software/answer/What-are-the-advantages-of-cycle-counting)
- Reconciliation pattern: Dynamics 365 makes spot counts create work that must be *accepted* before posting, rather than writing over the record silently. — [Microsoft Learn](https://learn.microsoft.com/en-us/dynamics365/supply-chain/warehousing/cycle-counting)

### Inferences
- **Treat each column sweep as a snapshot that replaces the column's contents.** A re-sweep of S2-07 replaces the box set for S2-07. Boxes that disappear become "not seen at S2-07 since <date>" rather than being deleted, so sold or moved boxes drop out of the "here now" view without losing history.
- **"Last seen" plus confidence decay.** Store `lastSeenAt` per (box barcode, location). Show an age badge such as "seen 3 days ago" or "seen 6 weeks ago". Lower the ranking or grey out old sightings. The decay-hazard literature supports a simple exponential confidence curve with a half-life tuned to how often the shop restocks. The half-life value itself must come from field data. I found no published value for shoe stock rooms.
- **Same model or barcode in several places.** This is normal: one model has many sizes, and the same size can sit in two stacks. The lookup should list *all* locations with counts and last-seen dates, sorted by freshness. A specific *box* ID (if per-box unique) seen in two columns means the older sighting is stale. If barcodes are only per model and size (EAN/GTIN), duplicates are expected and should be counted, not de-duplicated.
- **Sales.** If DİA/ERP sales export data is available, decrement or flag (model, size) quantities on a sale, but don't remove a location until a re-sweep confirms the box is gone. ERP sales tell you *what* left, not *which stack* it left from. Kang & Gershwin's finding about unrecorded loss suggests the physical sweep should be the source of truth for location, and the ERP the source for quantity.
- **Re-sweep scheduling for a small shop.** Adapt ABC to columns, not SKUs. Re-sweep columns holding fast movers (or recently restocked columns) weekly and the rest monthly. Add a "stale columns" list in the app (oldest sweep first), so re-counting is guided, not ad hoc. Gamma's result (twice a year beats once a year) suggests even modest regular re-sweeps help a lot.
- **Misplacement is the dominant failure.** DeHoratius & Ton's 60% "in store but not found" figure means a location map is valuable even where quantities are already known from the ERP.

### Gaps
- No published decay half-life or time-to-inaccuracy figure was found for backroom *location* records (as opposed to quantity records). The Chuang et al. full text, which may contain hazard estimates, was not accessible.
- The original Springer chapter text (DeHoratius & Ton) was behind a login. The 60%, 24% and 18% numbers come from search summaries of it.
- I found no small-shop (single stock room) IRI studies. All cited numbers come from multi-store chains.

## 4. Lookup UX: model search, fuzzy matching, scan-to-find, grid map, voice, hurried staff

### Takeaway
The proven retail pattern is "search, then show aisle/bay on a map" (Home Depot's Product Locator). Typo-tolerant autocomplete is a known best practice, yet 69% of e-commerce sites lacked it in Baymard's testing. On Android this can be built on-device with SQLite FTS5 trigram (substring) search plus an edit-distance library for typos. Voice search is feasible with the platform `SpeechRecognizer`, which has an explicit on-device mode from API 31. Touch targets should be at least 48dp.

### Cited Findings
- **Retail "find in store":** Home Depot's app Product Locator shows the exact aisle and bay on a map of the local store with one tap, and checks in-store stock. In-store mode switches on automatically. A typical store has ~35,000 items. — [Home Depot: How to find everything you need](https://www.homedepot.com/c/ai/find-everything-you-need-inside-the-home-depot-store/9ba683603be9fa5395fab901c3a65572); [Home Depot mobile app page](https://www.homedepot.com/c/mobile-app); [Home Depot corporate news](https://corporate.homedepot.com/news/company/hammers-nails-and-code-interconnected-shopping-experience)
- App store reviews report that this location and stock information is sometimes wrong. One reviewer called it "wishful thinking". This illustrates the staleness problem in section 3. — [Apple App Store: The Home Depot](https://apps.apple.com/us/app/id342527639) (via search summary)
- **Typo tolerance:** Baymard found 69% of sites don't show relevant autocomplete suggestions for closely misspelled queries. Users were hesitant to submit queries without the reassurance of matching suggestions. — [Baymard: Offer autocomplete suggestions for misspellings](https://baymard.com/blog/offer-autocomplete-suggestions-for-misspellings)
- **Edit-distance libraries (JVM/Kotlin):** tdebatty/java-string-similarity implements Levenshtein, Damerau-Levenshtein, Optimal String Alignment, Jaro-Winkler and others. It notes that Jaro-Winkler is designed for short strings and typos, and that only metric measures work with metric-tree indexes. Kotlin ports exist: kt-fuzzy (solo-studios, zero-dependency) and string-similarity-kotlin (Aallam). — [java-string-similarity (GitHub)](https://github.com/tdebatty/java-string-similarity); [kt-fuzzy (GitHub)](https://github.com/solo-studios/kt-fuzzy); [string-similarity-kotlin (klibs)](https://klibs.io/project/Aallam/string-similarity-kotlin)
- **Substring search on-device:** SQLite FTS5 has a built-in `trigram` tokenizer for substring matching (SQLite ≥ 3.34.0). Classic Room annotations support FTS3/FTS4 only. FTS5 needs a raw-SQL virtual table, the newer `room3` `@Fts5` annotation, or the bundled SQLite driver (`BundledSQLiteDriver`). A non-Android benchmark found trigram FTS5 much faster than `LIKE`, with a larger index. — [SQLite FTS5 docs](https://sqlite.org/fts5.html); [androidx room3 Fts5 reference](https://developer.android.com/reference/androidx/room3/Fts5); [CommonsWare: Room and FTS](https://commonsware.com/Room/pages/chap-roomfts-001)
- **Voice search on Android:** `SpeechRecognizer.createOnDeviceSpeechRecognizer()` (API 31+) creates an on-device recognizer. It throws `UnsupportedOperationException` if `isOnDeviceRecognitionAvailable()` is false. `checkRecognitionSupport()` and `triggerModelDownload()` (API 33+) check for and fetch language models. Error codes include `ERROR_LANGUAGE_UNAVAILABLE` (language supported but not downloaded). Results can include `CONFIDENCE_SCORES` (0–1) and multiple candidates in `RESULTS_RECOGNITION`, best first. Methods must run on the main thread, `RECORD_AUDIO` is required, and apps targeting API 30+ need a `<queries>` entry for `android.speech.RecognitionService`. The default recognizer "is likely to stream audio to remote servers". — [Android SpeechRecognizer reference](https://developer.android.com/reference/android/speech/SpeechRecognizer)
- `RecognizerIntent.EXTRA_PREFER_OFFLINE` is only a hint. AOSP notes it may have no effect depending on the recognizer and is heading toward deprecation. — [Android RecognizerIntent reference](https://developer.android.com/reference/android/speech/RecognizerIntent); [AOSP commit via /e/ GitLab](https://gitlab.e.foundation/e/os/android_frameworks_base/-/commit/d6975db81e3599ced4460712774b08bfb42a5cd2)
- **Touch targets:** Google recommends touch targets of at least 48×48dp (~9mm). This exceeds WCAG 2.2 AA (24×24 CSS px). Accessibility Scanner can check targets on the device. — [Google Android Accessibility Help: Touch target size](https://support.google.com/accessibility/android/answer/7101858?hl=en); [Android developers: Make apps more accessible](https://developer.android.com/guide/topics/ui/accessibility/apps)

### Inferences
- **Model-code search.** Codes like "0159 2000" are digit strings with optional spaces. Normalize them by removing spaces, dashes and dots and comparing digits only. Then rank as: exact match, then prefix match (e.g. "0159" lists all 0159-xxxx variants), then substring match (trigram), then edit distance ≤ 1–2 (Damerau-Levenshtein catches swapped digits such as "0195"). Show results while typing, because Baymard found users want the reassurance of matching suggestions. Use a numeric keypad by default for the search field.
- **Scan any box to find its siblings.** Scanning one box's barcode resolves its model, then shows the same result screen as a text search. This is the fastest path for staff holding a box and is consistent with "scan-first" WMS flows.
- **Voice.** Recognizers often return "zero one five nine two thousand" or "159 2000". Normalize number words and digit groups, and try all `RESULTS_RECOGNITION` candidates against the model index before showing "not found". Prefer on-device when available. Treat voice as optional, since stock rooms can be noisy and Turkish digit recognition quality is unverified.
- **Grid map.** A simple rows × columns grid that matches the physical label scheme (S{row}-{col}), with matching cells highlighted and a count badge, is the stock-room version of Home Depot's aisle/bay map. Also show the location code in very large text ("S2-07"), since a person in a hurry reads one code faster than a map.
- **For staff in a hurry.** One screen, big location text, 48dp+ targets, last-seen age on every result, and a one-tap "not there" button that marks the sighting stale. That button feeds the confidence decay in section 3.

### Gaps
- I did not verify any Nielsen Norman Group guidance on autocomplete or typo tolerance (the NN/g figure seen came from a secondary source, so I left it out).
- I found no published UX case studies of warehouse or stock-room pick apps' search screens. Only retail customer apps (Home Depot) were found.
- On-device Turkish speech recognition availability and digit accuracy are not documented in the sources. Test on the actual phone.

## 5. Size-level view: per model, which EU sizes are where and how many boxes

### Takeaway
I found no specific external source for a footwear "size × location" view. The building blocks are established, though: WMS location-content counts (Odoo shows per-location product quantities) and retail stock-by-store views. The design below is inferred.

### Cited Findings
- Odoo's location count lists every product assigned to a scanned location with a quantity, which is the location → contents view. The inverse (product → locations) is the lookup this app needs. — [Odoo 18 docs](https://www.odoo.com/documentation/18.0/applications/inventory_and_mrp/barcode/operations/adjustments.html)
- Home Depot pairs location with in-store stock count in one view. — [Home Depot: Product Locator guide](https://www.homedepot.com/c/ai/find-everything-you-need-inside-the-home-depot-store/9ba683603be9fa5395fab901c3a65572)
- Product categories explain much more record-inaccuracy variance (26.4%) than stores do (2.7%). Some product types are reliably messier, so a per-model view should show how fresh the data is. — [DeHoratius & Raman 2008](https://pubsonline.informs.org/doi/10.1287/mnsc.1070.0789)

### Inferences
- **Layout:** a model header (code, name, total boxes seen), then a table with one row per EU size (36, 37, … 45) and columns *location chips* ("S2-07 ×2", "S3-01 ×1"), *total*, and *last seen*. Sizes with zero sightings appear greyed out ("none seen"). This answers the most common question, "do we have a 42 and where?".
- **Toggle view:** location-major ("S2-07: 40×1, 41×2, 42×1"), useful when the person is already standing at a column.
- If the ERP or DİA quantity per size is available, show "ERP: 3 / seen: 2". A mismatch flags a likely misplaced box or a needed re-sweep, which turns the lookup screen into a cycle-count trigger.
- The size data must come from the box barcode (GTIN mapped to model and size) or from OCR of the label. The mapping source is outside this research scope.

### Gaps
- No external examples or studies of size-matrix location views for footwear backrooms were found.
- I found no evidence on how many sizes per model a small shop typically stocks, or how often one size is split across columns.
