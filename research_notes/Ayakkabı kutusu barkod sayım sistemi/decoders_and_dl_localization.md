# Barcode detection/decoding for many small Code 128 labels in a moving Android camera feed (incl. DL localization)

Research date: 2026-11-14. Context: SweepScan (Kotlin, Galaxy S23 Ultra / Snapdragon 8 Gen 2), CameraX ImageAnalysis 1080p -> ML Kit bundled 17.3.0 with enableAllPotentialBarcodes -> zxing-cpp 3.1.1 on undecoded crops -> tracker. Labels: ~5 cm wide barcode, 13 numeric digits, very likely Code 128.

Research budget note: several primary PDFs (BarBeR ICPR 2024 full paper, EAAI 2025 review, CAIP 2025 BaFaLo paper, OpenCV docs) returned HTTP 403 to the fetch tool, so their result tables could not be read directly. What is reported below about them comes from abstracts, search snippets, or the RRPR reproducibility paper, and is flagged as such.

## 1. ML Kit barcode scanning: versions, bundled vs unbundled, image requirements, performance tips, known issues

### Takeaway
ML Kit Android barcode artifacts have not changed since 7 Aug 2024 (bundled 17.3.0, unbundled 18.3.1; that release only added 16 KB page-size support), so SweepScan is already on the latest version and no newer model is coming from Google through Nov 2026. Google's own rule is "smallest unit at least 2 pixels wide"; for a 13-digit Code 128 that works out to roughly 250 px of barcode width in the frame (inference below), which a 1080p frame covering a whole column of boxes probably does not provide.

### Cited Findings
- Latest Android versions: `com.google.mlkit:barcode-scanning:17.3.0` (bundled) and `com.google.android.gms:play-services-mlkit-barcode-scanning:18.3.1` (unbundled), both dated 08/07/2024. The only stated change was "Updated Android SDKs to support 16 KB page sizes". Every release table from 29 Aug 2025 through 26 Oct 2026 marks the Android barcode artifacts as unchanged — [ML Kit release notes](https://developers.google.com/ml-kit/release-notes)
- No accuracy improvements are listed for 2024–2026. The last accuracy note is from 23 Aug 2022: the unbundled Android API got "Improved recall, long tail latency, low-quality image tolerance and bounding box stability". Return-all-potential-barcodes arrived on 21 Mar 2023 and auto-zoom on 1 Aug 2023 — [ML Kit release notes](https://developers.google.com/ml-kit/release-notes)
- Bundled vs unbundled: unbundled is "About 200 KB size increase" (model delivered through Google Play Services); bundled is "About 2.4 MB size increase" (model linked at build time). Requires API 23+. The docs describe no accuracy difference between the two — [ML Kit Android barcode guide](https://developers.google.com/ml-kit/vision/barcode-scanning/android)
- Image requirements, quoted: "the smallest meaningful unit of the barcode should be at least 2 pixels wide"; "Because an EAN-13 barcode is 95 units wide in total, the barcode should be at least 190 pixels wide." Also: "Poor image focus can impact scanning accuracy." Recommended input: "1280x720 or 1920x1080" — [ML Kit Android barcode guide](https://developers.google.com/ml-kit/vision/barcode-scanning/android)
- Performance tips, quoted: "Don't capture input at the camera's native resolution"; request only the size needed for detection, "which is usually no more than 2 megapixels"; for Camera/camera2, "If a new video frame becomes available while the detector is running, drop the frame"; for CameraX, keep `STRATEGY_KEEP_ONLY_LATEST`, which "guarantees only one image will be delivered for analysis at a time"; "wait until you get a consecutive series of the same value to be confident" — [ML Kit Android barcode guide](https://developers.google.com/ml-kit/vision/barcode-scanning/android)
- `enableAllPotentialBarcodes()`: available from bundled 17.1.0 / unbundled 18.2.0. It returns "all potential barcodes even if they cannot be decoded" — [ML Kit Android barcode guide](https://developers.google.com/ml-kit/vision/barcode-scanning/android)
- `ZoomSuggestionOptions` (auto-zoom): available from bundled 17.2.0 / unbundled 18.3.0. A zoomCallback is required and "will always be called on the main thread". `maxSupportedZoomRatio` should be set from camera hardware; without it "an unbounded zoom ratio might be produced". The scanner can keep asking for more zoom until the max is reached — [ML Kit Android barcode guide](https://developers.google.com/ml-kit/vision/barcode-scanning/android)
- Known issue #32, "MLKit Vision is reading code128 and 39 barcodes poorly" (opened Feb 2019, now closed): random or wrong characters in Code 128/39 with no error raised, e.g. "N51%%3"; partial barcodes read as if complete (Nov 2021: "causing production problems"; ZXing does not do this); still reported on the latest versions in Oct 2022. Google said it might favor complete barcodes in future releases. No confirmed fix — [googlesamples/mlkit #32](https://github.com/googlesamples/mlkit/issues/32)
- Other relevant issues: #145 "barcode scanner scan one barcode multiple times and some times not complete" (closed Oct 2020); #376 "Multiple detections at once?" (closed Nov 2021); #549 multiple barcodes / filter option for GmsBarcodeScanner (open since Jul 2022); #1053 DPM Data Matrix not detected (open, May 2026). Searching the issue list found nothing specific to enableAllPotentialBarcodes, zoom suggestion, or small barcodes — [googlesamples/mlkit issues search](https://github.com/googlesamples/mlkit/issues?q=barcode+multiple)
- Stack Overflow report of Code 128 "PAN/230954" read as "PAN/2 30954" (an extra character), with no answer. Another thread reports ML Kit missing Code 128 longer than about 30–35 characters; one answer ties this to the minimum pixel width needed per character — [SO mirror: wrong scans](https://kiwix.lema.org/stackoverflow.com_en_all_2023-11/questions/69847084/ml-kit-barcode-scanner-picks-up-wrong-scans-sometimes); [SO mirror: >30 chars](https://kiwix.lema.org/stackoverflow.com_en_all_2023-11/questions/63919991/not-able-to-read-more-30-chars-barcode-using-firebase-ml-kit)

### Inferences
- **What the 190 px rule means for a 13-digit Code 128.** I computed this from the Code 128 symbol structure; it is not stated in any source. Each Code 128 symbol is 11 modules and the stop is 13. Thirteen digits is an odd count, so the encoder uses Start B + 1 digit + CODE C + 6 digit pairs (or Start C + 6 pairs + CODE B + 1 digit). That gives start + 8 data symbols + checksum = 10 × 11 = 110 modules, plus a 13-module stop, so **about 123 modules** before quiet zones (each quiet zone is ≥10 modules). At ML Kit's 2 px/module that is **about 246 px of barcode width (about 286 px with quiet zones)**, which is 30% more than EAN-13's 190 px. An encoder that does not optimize (all Code B) would need 13 data symbols, about 178 modules and about 356 px.
- **Physical scale.** A 5 cm barcode with about 123 modules gives a module of about 0.41 mm. Reaching 2 px/module takes about 4.9 px per mm on the label. With the 1920 px side of a 1080p frame across the scene, the field of view can be at most about 39 cm wide. At 1440p (2560 px) the limit is about 52 cm, and at 4K (3840 px) about 78 cm. If one frame is meant to cover a whole column of boxes plus margin, 1080p is likely below threshold. A frame that shows 20+ labels very probably means fewer than 2 px/module.
- Google's "≤2 MP" tip assumes one barcode that fills a good part of the frame. Small-label, many-label scenes fall outside that design case, so higher analysis resolution or optical/digital zoom is the main lever.
- ZoomSuggestionOptions is built for a single target that is too small (it asks for zoom-in rounds). For a sweep that needs a wide field of view to count many labels, auto-zoom works against coverage. Use it at most as a hint, or leave it off.
- Issue #32 (partial reads and wrong characters on Code 128) means ML Kit results need validation. The value is always 13 digits, so require exactly 13 numeric characters, optionally check against a known prefix or SKU list, and require agreement across several frames (as Google's own docs recommend). In a dense scene, a partial read of one barcode could plausibly yield a different valid-looking string, which matters for counting.

### Gaps
- No official statement on whether the bundled (17.x) and unbundled (18.x) models differ in accuracy. The 2022 recall improvement was announced only for the unbundled API, so the Play Services model may be newer, but this is unverified. An A/B test on the device is needed.
- No official numbers on how many barcodes ML Kit returns per frame, or on accuracy as barcode count grows. I found no googlesamples issue that quantifies misses in scenes with 10–20+ barcodes.
- No documented internal resolution or downscaling of the ML Kit detector, so its effective pixels per module after any internal resize is unknown.

## 2. zxing-cpp vs ML Kit vs ZXing (Java): accuracy, speed, options, multi-symbol reading

### Takeaway
zxing-cpp is actively maintained: v3.1.1 is the latest stable (29 Jul 2026), and v3.2.0-rc1 shipped 13 Nov 2026 with a 43% smaller Android binary and a Code 128 fix. On the only large independent-dataset comparison found (vendor-run, on BarBeR), it had about 72% recall and 95.8% precision, versus 92.8% recall for Dynamsoft. No published head-to-head with ML Kit was found. For Code 128 crops, the options that matter are tryHarder, tryRotate=false (the orientation is known), tryDownscale, binarizer, minLineCount and the formats filter.

### Cited Findings
- Release timeline (year inferred from the order: v3.0.0 in Feb, after v2.3.0 in Jan): v3.2.0-rc1 on 13 Nov (pre-release), v3.1.1 on 29 Jul (latest stable), v3.1.0 on 7 Jul, v3.0.0 on 10 Feb, v2.3.0 on 1 Jan — [zxing-cpp releases](https://github.com/zxing-cpp/zxing-cpp/releases)
- v3.2.0-rc1: Android binary cut by 43% (1,747 KB to 988 KB); "Code128 now ignores checksum function code effects"; HybridBinarizer 2D thresholding 1–50% faster; `ReadBarcodes()` in isPure mode returns an empty list instead of an invalid barcode. v3.1.0: 10–40% speed-ups "especially on ARM"; Code 128 processes the 1st/2nd-position FNC1 only once; much better QR detection of many small symbols per image; a `BarcodeFormat` filtering regression in ReadBarcodes fixed. v3.0.0: 16 KB page alignment for Android — [zxing-cpp releases](https://github.com/zxing-cpp/zxing-cpp/releases)
- The README claims "many improvements in terms of runtime and detection performance" over the Java ZXing it was ported from. It gives no figures and makes no comparison with ML Kit. The library is thread safe — [zxing-cpp README](https://github.com/zxing-cpp/zxing-cpp)
- ReaderOptions (quoted from the header comments): tryHarder "optimize for accuracy instead of not speed (default: true)"; tryRotate (default true); tryInvert (default true); tryDownscale "Try detecting code in downscaled images (depending on image size) (default: true)"; binarizer default `Binarizer::LocalAverage`; minLineCount "The number of scan lines in a linear barcode that have to be equal to accept the result (default: 2)"; maxNumberOfSymbols "maximum number of symbols (barcodes) to detect / look for with ReadBarcodes()"; isPure for synthetic single-barcode images; downscaleThreshold/downscaleFactor (2, 3, 4); returnErrors (default false); validateOptionalChecksum (default false; Code 128's checksum is mandatory, so it is always checked) — [ReaderOptions.h](https://raw.githubusercontent.com/zxing-cpp/zxing-cpp/master/core/src/ReaderOptions.h)
- **Vendor benchmark (Dynamsoft, page "Updated Nov 06, 2026"), on 7,894 deduplicated BarBeR images with 8,411 scored barcode instances, Intel i5-13400F, one thread, decoder call only:** Dynamsoft Barcode Reader 11.6: 92.81% recall, 95.85% precision, 1.09% wrong reads, mean / median / P95 time 57.1 / 39.5 / 157.4 ms. ZXing-C++ 3.1.1: 71.70% recall, 95.79% precision, 1.19% wrong reads, 27.11% no-read, 69.9 / 44.7 / 227.6 ms. No per-format (Code 128) breakdown — [Dynamsoft C++ benchmark](https://www.dynamsoft.com/codepool/benchmark-barcode-reading-cpp-zxing-dynamsoft-barcode-reader.html). **Bias flag:** run and published by a competing commercial vendor. A search snippet of what appears to be an earlier version or sibling article (Python) showed different figures: DBR 86.78% recall vs ZXing-C++ 67.43% — [Dynamsoft benchmark tag page](https://www.dynamsoft.com/codepool/tag/barcode-benchmark); [Dynamsoft Python benchmark](https://www.dynamsoft.com/codepool/benchmark-barcode-reading-python-zxing-dynamsoft-barcode-reader.html). The two versions disagree, so treat the absolute numbers as approximate.

### Inferences
- For SweepScan's second pass on crops ML Kit located but could not decode, suggested zxing-cpp settings: `formats = Code128` only (faster, and no false positives from other symbologies); `tryRotate = false` if the label orientation in the frame is known; `tryInvert = false`; `tryHarder = true`; `tryDownscale = false` on small crops (downscaling a small barcode removes the modules you need, so you may even want to upscale 2x before calling); `minLineCount = 2` or 3 (raising it trades recall for fewer misreads); `maxNumberOfSymbols = 1` per crop. Try `Binarizer.LocalAverage` first, then `GlobalHistogram` as a fallback on the same crop, since one may decode a blurry or low-contrast crop the other fails on (my suggestion, not benchmarked).
- zxing-cpp's precision (95.8%) was on par with a commercial SDK in the vendor test. Its weakness is recall on hard images. That fits SweepScan's design of ML Kit as primary plus zxing-cpp as a rescue decoder on crops, rather than replacing ML Kit.
- Upgrading to 3.2.0 when it goes stable is low-risk and gives a smaller APK. The Code 128 change concerns function codes, which numeric labels should not use.

### Gaps
- No independent published benchmark of zxing-cpp vs ML Kit on the same images was found, nor zxing-cpp vs ZXing Java numbers in the official repo (the README gives no figures). zxing-cpp's own blackbox test pass rates were not retrieved.
- No published ms-per-1080p-frame figure for zxing-cpp on Snapdragon 8 Gen 2 / Cortex-X3 was found. The only timing found is the x86 i5-13400F figure above (mean 69.9 ms per image of mixed sizes). On small crops it should be well under that, but this must be measured on the device.
- Scanbot and barKoder comparison pages were not retrieved within the budget. They would be vendor-biased in any case.

## 3. OpenCV barcode module (cv::barcode / objdetect BarcodeDetector)

### Takeaway
OpenCV's BarcodeDetector (moved to `objdetect` in 4.8, with Java bindings as `org.opencv.objdetect.BarcodeDetector`) has an optional WeChat super-resolution CNN. The formats confirmed by the sources reached are EAN/UPC only, and Code 128 support could not be confirmed, so it is not a good fit for SweepScan's Code 128 labels.

### Cited Findings
- The Java BarcodeDetector constructor takes a prototxt path and a model path to load an "_optional_ Super Resolution DNN model for better quality". The 4.7 tutorial uses sr.prototxt / sr.caffemodel from WeChatCV's opencv_3rdparty. The 5.0 tutorial gives compatibility as OpenCV >= 4.8 and references an sr.onnx model. Java docs exist for 4.9.0 and 4.x under `org.opencv.objdetect` — [OpenCV 4.9 Java doc (search result)](https://docs.opencv.org/4.9.0/javadoc/org/opencv/objdetect/BarcodeDetector.html); [OpenCV 4.7 tutorial](https://docs.opencv.org/4.7.0/d6/d25/tutorial_barcode_detect_and_decode.html); [OpenCV 5.0 tutorial](https://docs.opencv.org/5.0/tutorials/objdetect/barcode_detect_and_decode/barcode_detect_and_decode.html)
- Older bindings list only EAN-13, EAN-8, UPC-A and UPC-E as barcode type constants — [opencv-rust barcode docs 0.80](https://docs.rs/crate/opencv/0.80.0/source/docs/barcode.rs)

### Inferences
- Even if newer OpenCV versions decode Code 128, the gradient-orientation localizer plus SR model is mainly interesting as a localization or upscaling stage. Pulling in the OpenCV Android SDK (tens of MB) for that is a heavy dependency compared with ML Kit + zxing-cpp.
- The WeChat SR model (designed for small QR/barcode crops) could in principle be borrowed as an upscaler for small Code 128 crops before zxing-cpp. Its effect on 1D codes is unbenchmarked.

### Gaps
- OpenCV docs returned 403, so the current supported-format list (Code 128 / Code 39 in 4.8–4.10+) and any accuracy figures could not be verified. No independent accuracy benchmark for OpenCV BarcodeDetector on 1D codes was found.

## 4. Academic benchmarks and datasets for 1D barcode detection/decoding

### Takeaway
BarBeR (UniMoRe, ICPR 2024; EAAI 2025 review) is the largest open benchmark: 8,748 images and 9,818 barcodes, of which 8,062 are 1D, each annotated with PPE (pixels per element). It shows that the field has largely moved to DL localizers (YOLO, Faster R-CNN). A CAIP 2025 paper from the same group reports a light localizer matching YOLO Nano decode rates on 1D. Older public 1D datasets (InventBar, ParcelBar) contain no small barcodes, so they say little about SweepScan's main difficulty.

### Cited Findings
- BarBeR dataset: 8,748 images, 9,818 annotated barcodes (8,062 linear, 1,756 2D). Each annotation includes polygon, type, PPE ("pixels per element, other times referred to as PPM or pixels per module") and the encoded string. Classes include Code 128, Code 39, EAN-8/13, GS1-128, ITF and more. Resolutions range from 200×141 to 5,984×3,376; images include blur, noise, skew/warp, occlusion and over- or under-exposure — [BarBeR RRPR 2024 reproducibility paper](https://rrpr2024.sciencesconf.org/data/RRPR_2024_paper_10.pdf)
- BarBeR includes these localizers: Gallo, Sörös, Yun, Zamberletti, Zharkov (DL, multi-label), and Ultralytics (YOLO, RT-DETR), Detectron2 and PyTorch models. Metrics are P/R/F1 at several IoU thresholds, AP/mAP and AR, and F1 broken down by PPE bins. Timing was measured on a Threadripper Pro 5965WX + RTX 4090 and on a Raspberry Pi 3B+. Multi-class tests used input scaled so the longest side is 640, 480 and 320 px. All detection tests used 5-fold cross-validation — [BarBeR RRPR paper](https://rrpr2024.sciencesconf.org/data/RRPR_2024_paper_10.pdf)
- The BarBeR repo has a decoding test (`test_decodings.py`: detect, crop, decode with pyzbar, report % decoded for 1D/2D). The repo is AGPL-3.0, and the dataset requires an account to download — [BarBeR GitHub](https://github.com/Henvezz95/BarBeR); [BarBeR dataset page](https://ditto.ing.unimore.it/barber)
- Citations: Vezzali, Bolelli, Santi, Grana, "BarBeR: A Barcode Benchmarking Repository," ICPR 2024, LNCS 15317, pp. 187–203 (2025); and "State-of-the-art Review and Benchmarking of Barcode Localization Methods," Engineering Applications of AI vol. 147 (2025). Between 2015 and 2021, 25 publications introduced DL barcode localization methods, and YOLO and Faster R-CNN are the most used — [UniMoRe IRIS ICPR record](https://iris.unimore.it/handle/11380/1377708); [UniMoRe IRIS EAAI record](https://iris.unimore.it/handle/11380/1372451) (via search snippets; full text 403)
- CAIP 2025 (same group), BaFaLo: "decoding rate nearly equivalent to YOLO Nano for 1D barcodes and only 3.5 percentage points lower for 2D barcodes while being approximately nine times faster", at 57.62 ms per frame on one Raspberry Pi 3B+ core — [UniMoRe IRIS CAIP 2025 record](https://iris.unimore.it/handle/11380/1379508) (search snippet; PDF 403)
- InventBar / ParcelBar (Kamnardsiri et al., Sensors, 14 Nov 2022): InventBar has 527 grocery images at 4032×3024 (Galaxy S10+) with 527 1D barcodes; ParcelBar has 844 warehouse post-box tag images with 1,088 barcodes. Neither contains small barcodes. Detection mAP@0.5 is about 0.95–0.998 for all five DL detectors; mAP@0.5:0.95 is best for YOLOv5 (0.873 / 0.918). There is no comparison with classic methods and no separate blur results; small and distant barcode detection is listed as future work. Datasets are free at cmu.to/BenchmarkBarcodeDatasets — [Sensors 2022, PMC9696533](https://pmc.ncbi.nlm.nih.gov/articles/PMC9696533/)
- YOLO-Barcode (Ershova, Gayer, Bezmaternykh, Arlazarov; Smart Engines; Computer Optics 48(4), 2024): built for "a large number of densely spaced barcodes" and highly elongated 1D codes. F1 is 98.6% vs 88.9% for DilatedModel on ZVZ-real, about 4× faster, and 92.11% on the new SE-barcode dataset — [Computer Optics 2024](https://computeroptics.ru/eng/KO/Annot/KO48-4/480414e.html). Bias flag: Smart Engines is a commercial vendor, though this is a peer-reviewed journal.
- arXiv 2511.22937 (Nov 2025, INNOCOMP 2024): YOLOv8 n/s/m on Kaggle barcode+QR data, "accuracy" 88.95% / 97.10% / 94.10%. Low-detail paper with no small-barcode analysis — [arXiv 2511.22937](https://arxiv.org/abs/2511.22937v1)

### Inferences
- Across these sources, DL localizers reliably find barcodes. The bottleneck for small or blurred 1D codes is decoding at low PPE, not localization. The BaFaLo result (a light localizer about equal to YOLO Nano on 1D decode rate) suggests a heavier DL localizer does not by itself raise 1D decode rate.
- For SweepScan, the most transferable evidence is the PPE framing. Decode rate depends on pixels per module, so analysis resolution and zoom matter more than the choice of localizer.
- BarBeR could be used to benchmark ML Kit vs zxing-cpp on Code 128 by PPE bin (it has PPE annotations and encoded strings). Its AGPL code license matters only if code is shipped, not for offline evaluation.

### Gaps
- Exact BarBeR/EAAI result tables (F1 per method, F1 vs PPE curves, decoder rates by PPE) could not be read because the PDFs returned 403, so there is no number for "decode rate at PPE < 2 vs > 3".
- The Muenster BarcodeDB, Arte-Lab (Zamberletti) and Dubská datasets were not individually checked in this pass. They are known to be included in BarBeR, but this was not verified per dataset.
- No academic benchmark including Google ML Kit as a decoder was found.

## 5. Deep-learning barcode localization: pretrained models, licenses, on-device speed, and whether DL beats ML Kit for many small 1D labels

### Takeaway
Off-the-shelf YOLOv8s barcode checkpoints exist on Hugging Face (Ultralytics-based, so AGPL-3.0 unless you hold an Enterprise license). A YOLOv8 detector at 640 input runs in about 1.5 ms (INT8) to 5–7 ms (FP16) on the Galaxy S23 NPU according to Qualcomm AI Hub, so speed is not the blocker. I found no evidence that DL localization beats ML Kit for many small 1D labels. A DL detector only helps if its boxes are decoded from a high-resolution frame that has enough pixels per module.

### Cited Findings
- Hugging Face YOLOv8s barcode models (e.g. Piero2411/YOLOV8s-Barcode-Detection, amir-salar/YOLOV8s-Barcode-Detection, chinhong11/YOLOV8s-Barcode-Detection) are fine-tuned Ultralytics YOLOv8s for barcode and QR detection, distributed as .pt. Export to TFLite with `model.export(format="tflite", imgsz=640, nms=True)` — [HF Piero2411](https://hface.pages.dev/Piero2411/YOLOV8s-Barcode-Detection); [HF amir-salar](https://huggingface.co/amir-salar/YOLOV8s-Barcode-Detection); [HF chinhong11](https://huggingface.co/chinhong11/YOLOV8s-Barcode-Detection); [Roboflow mobile detection models](https://blog.roboflow.com/mobile-object-detection-models/)
- BarBeR's pretrained Ultralytics/Detectron2 barcode models are downloadable from the dataset site, and the repo is AGPL-3.0 — [BarBeR GitHub](https://github.com/Henvezz95/BarBeR)
- On-device speed, YOLOv8-Detection on a Galaxy S23 (Snapdragon 8 Gen 2), Qualcomm AI Hub cards: FP16 TFLite on NPU about 5.2–7.4 ms (5.673 ms TFLite vs 3.952 ms QNN in one listing); w8a8 TFLite about 1.5 ms. Figures vary by card version — [Qualcomm YOLOv8-Detection (HF)](https://huggingface.co/qualcomm/YOLOv8-Detection); [Qualcomm YOLOv8-Detection-Quantized (HF)](https://huggingface.co/qualcomm/YOLOv8-Detection-Quantized); [Qualcomm AI Hub yolov8_det](https://aihub.qualcomm.com/models/yolov8_det). These are COCO-model timings at default input (640), not barcode-specific. Qualcomm's AI Hub YOLOv8 cards also carry Ultralytics' AGPL licensing (not verified on the card page in this pass).
- Dynamsoft tutorials show YOLO-based QR localization on Android followed by a commercial decoder (QR only, vendor content) — [Dynamsoft Android YOLO + DBR](https://www.dynamsoft.com/codepool/android-qr-code-recognition-yolo-dynamsoft-barcode.html)
- YOLO-Barcode (Smart Engines) explicitly targets dense, many-barcode scenes on mobile, with 98.6% F1 on ZVZ-real (see Section 4). The model is not public — [Computer Optics 2024](https://computeroptics.ru/eng/KO/Annot/KO48-4/480414e.html)

### Inferences
- **Where DL could help SweepScan:** (a) a custom detector trained on SweepScan's own label crops (one class, "shoe label") could find all labels even when barcodes are too small to decode, giving the tracker a reliable expected count per column and a signal of what was missed. It can also localize the white label itself, which is much larger and higher-contrast than the bars. (b) Its boxes could drive a high-resolution crop pipeline (e.g. a 4K still or a high-res analysis frame) where each crop is decoded by zxing-cpp/ML Kit at full resolution.
- **Where it won't help:** a YOLO model at 640 input sees a 1080p frame downscaled about 3×, so it cannot decode anything itself. Running localization at 640 and decoding on the same low-resolution image gives no gain. ML Kit's enableAllPotentialBarcodes already provides undecoded boxes, which is the same thing a generic barcode YOLO would add, so a generic pretrained YOLO is probably redundant with the current pipeline unless ML Kit is shown to *miss locating* labels (vs. failing to decode them).
- **Licensing:** Ultralytics YOLOv5/v8/v11 code and weights derived from it are AGPL-3.0. Shipping in a closed commercial app needs an Ultralytics Enterprise license. Permissive alternatives: train with a permissively licensed detector stack (e.g. MediaPipe/TFLite Model Maker EfficientDet-Lite, or other MIT/Apache YOLO-family re-implementations), then run via LiteRT with the GPU delegate or QNN/NNAPI. Verify each project's license before use.
- **Deblurring/super-resolution:** the evidence found covers only the OpenCV/WeChat SR model (Section 3). No barcode-specific deblurring benchmark on 1D codes was found, so exposure control (Section 6) should be preferred over post-hoc deblurring.

### Gaps
- No published comparison of ML Kit localization recall vs a YOLO barcode detector on dense small 1D scenes was found. It must be measured on SweepScan's own footage (log ML Kit potential-barcode boxes vs hand-labelled labels).
- Training data and licenses of the Hugging Face YOLOv8s barcode checkpoints were not verified per model card (likely Kaggle/Roboflow data; AGPL via Ultralytics).
- Roboflow Universe barcode datasets/models were not enumerated in this pass.
- No LiteRT GPU-delegate (vs NPU) timing for YOLO on the S23 was found; only Qualcomm AI Hub NPU figures.

## 6. Effect of analysis resolution (1080p / 1440p / 4K) and motion blur

### Takeaway
At about 0.41 mm per module, 2 px/module limits a 1080p frame (1920 px wide) to about a 39 cm field of view, 1440p to about 52 cm, and 4K to about 78 cm. This makes resolution or zoom the dominant factor for small 13-digit Code 128 labels. Motion blur along the bars is nearly harmless, while blur across the bars must stay at or below about 1 module (≈0.4 mm), which means very short exposures if the sweep is across the bars. These are geometric inferences; no published measurement specific to this setup was found.

### Cited Findings
- ML Kit recommends 1280×720 or 1920×1080 and "usually no more than 2 megapixels" for speed, with the 2 px/module rule — [ML Kit Android barcode guide](https://developers.google.com/ml-kit/vision/barcode-scanning/android)
- BarBeR reports localization at longest side 640, 480 and 320 px and F1 by PPE bin, confirming PPE as the controlling variable in the benchmark design — [BarBeR RRPR paper](https://rrpr2024.sciencesconf.org/data/RRPR_2024_paper_10.pdf)
- ML Kit "Poor image focus can impact scanning accuracy" — [ML Kit Android barcode guide](https://developers.google.com/ml-kit/vision/barcode-scanning/android)

### Inferences
- **Resolution math:** module ≈ 50 mm / 123 ≈ 0.41 mm (Section 1). Required ≥ 2 px/module means ≥ 4.9 px/mm. Maximum horizontal field of view = frame width / 4.9: 1080p ≈ 39 cm, 1440p ≈ 52 cm, 4K ≈ 78 cm. For safety margin (2.5–3 px/module, since blur and perspective eat pixels), divide by 1.25–1.5. In portrait orientation, use the 1080/1440/2160 px side if the barcodes run across the short axis, which halves these numbers.
- **Frame rate vs resolution:** ML Kit cost grows roughly with pixel count. 4K is 4× the pixels of 1080p, so at constant per-pixel cost expect about 4× latency, though there is no measured figure for the S23. A hybrid design is likely best: run ML Kit at 1080p for tracking and localization, and decode high-resolution crops (from a parallel higher-resolution stream or from zxing-cpp on crops of a 4K/1440p frame) only where boxes are undecoded.
- **Motion blur:** blur length = sweep speed × exposure time. Bars on a short-end label are likely vertical (barcode horizontal). If the phone sweeps vertically along a column, the motion is parallel to the bars and smears along them, which barely changes the 1D bar profile. Horizontal motion is what destroys decoding. For cross-bar motion at 0.5 m/s, keeping blur ≤ 0.4 mm (1 module) needs exposure ≤ 0.8 ms (≈1/1250 s). At a typical indoor auto-exposure of 1/60–1/120 s, blur would be 4–8 mm (10–20 modules), which is undecodable. Recommendation: sweep parallel to the bars, and/or cap exposure via Camera2 interop (CONTROL_AE_TARGET_FPS_RANGE / manual SENSOR_EXPOSURE_TIME with ISO compensation) and use good lighting or the torch.
- Continuous autofocus hunting during a sweep can blur frames. Locking focus at the working distance may help, but this is unverified.

### Gaps

- No published motion-blur tolerance thresholds for ML Kit or zxing-cpp on Code 128 were found. The figures above are geometric inferences.
